# decision-aware-design

Before using Sundial, locate and read `sundial/SUNDIAL-INSTRUCTIONS.md` from the project root and follow its shared workflow guidance.

1. Run `sundial domains` to get the list of known domains.
2. Select all relevant domains for the task.
3. Retrieve accepted DRs with one call: `sundial dr retrieve [--domain <domain>]...`.
 * Repeat `--domain` for each relevant domain. Domain retrieval matches ancestors, the exact domain, and descendants. Excluding all domain flags matches all domains.
4. Indicate to the user which DRs are being applied.

Optional spec-driven development:
 * Use a spec when the user asks for one, when an existing `SPEC-*` is the working context, or when a non-trivial feature/design would benefit from a living implementation scratchpad. Do not create specs for small one-off tasks unless the user asks or the work clearly needs one.
 * Create new specs only through the CLI: `sundial spec create --title "<title>" [--status <lane>]`. Use `sundial spec lanes` to see valid statuses. Do not hand-create spec files or `board.md`.
 * The spec template is the markdown generated by `sundial spec create` from `packages/cli/src/core/specs.ts#renderSpecMarkdown`: Requirements, Discovery, scope exclusions, Applicable Research Notes, Applicable Decision Records, Open Questions, Data Model Changes, Final Interface Changes, Final Implementation Structure, Files and Functions, Code Snippets, Test Plan, Implementation Log, and Test Log.
 * If operating against a spec, cite the spec id/title in updates and keep requirements, scope exclusions, approach details, open questions, and test expectations current.
 * Update spec status only through the CLI: `sundial spec status <id> <status>` or `sundial spec update-status <id> <status>`.
 * Edit the spec markdown body directly when filling or refining the template. Keep specs living and forward-looking; reserve backward-looking execution details for Implementation Log and Test Log.
 * When invoked by a one-line Sundial planning launch prompt, treat the request as the planning phase: avoid implementing feature code, but write or run small probes when needed to validate assumptions; keep Requirements, scope exclusions, Approach, Test Plan, and Open Questions current.

Research note discipline:
 * When design work required concrete research that future agents are likely to misremember, such as API signatures, CLI flags, protocol details, provider extension command ids, URI schemes, version-specific behavior, or official-doc findings, use the `remember-research` skill after the design pass.
 * Store only findings and unknowns under `sundial/research/` with the shared domain vocabulary, then cite the research id in any active spec's `Applicable Research Notes`.
 * Keep recommendations, next steps, and design implications in specs, implementation plans, or DR candidates instead of research notes.
 * Do not use research notes for governing rules; propose a DR candidate instead when the finding should constrain future design or implementation.
